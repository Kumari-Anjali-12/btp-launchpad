SAP BTP + AI Developer Syllabus
Prepared for Nikky. All 9 phases, from pre-learning to the capstone.
Assumptions
Topic: SAP BTP development with an AI layer, following the 9-phase roadmap.
Level: Complete SAP fresher, final-year CSE (AI and ML) student, comfortable with Odoo development.
End goal: A deployed capstone (a CAP app with an AI feature on BTP) and a portfolio, not a certification.
Pacing: About 16-18 weeks at roughly 8-12 hours a week.
BTP's cockpit labels and trial limits change, so check any button name or quota against SAP Help Portal.
Phase 0: Pre-learning
Core Objective: Read SAP and BTP documentation without stalling. By the end you can explain the SAP landscape, consume and write OData and REST calls, write asynchronous Node.js and TypeScript, use Git, the command line and Docker, and explain OAuth 2.0 and JWT validation.
Estimated Time: about 30 hours over 3 weeks. Keep it light while your semester exams run.
Module 0.1: SAP World Basics
Granular Sub-topics & Mechanics:
ERP concept: one integrated database and process layer across finance, procurement, sales, inventory, production and HR.
Product map: SAP ECC (legacy ERP), SAP S/4HANA (current ERP suite), SAP HANA (in-memory column-store database), SAP Fiori (UX design system and launchpad), SAP BTP (platform for extending and integrating SAP systems).
S/4HANA deployment options: Cloud Public Edition, Cloud Private Edition, on-premise.
Functional areas and their classic codes: FI (Financial Accounting), CO (Controlling), MM (Materials Management), SD (Sales and Distribution), PP (Production Planning), QM (Quality Management), PM (Plant Maintenance), EWM (Extended Warehouse Management). Human resources lives mainly in SuccessFactors.
End-to-end processes: Procure-to-Pay (purchase requisition, purchase order, goods receipt, invoice receipt, payment), Order-to-Cash (sales order, delivery, billing, payment), Plan-to-Produce, Record-to-Report.
Data kinds: master data (material master, business partner, chart of accounts) versus transactional data (documents).
Organisational units: client, company code, plant, storage location, sales organisation, purchasing organisation.
Landscape and terms: development, quality and production systems, transports, tenants, T-codes, BAPI, IDoc, RFC, ABAP, CDS view, OData service, SAP Business Accelerator Hub.
Clean core: why modifying standard SAP code makes upgrades painful, and the three extension styles (in-app key-user extensibility, developer extensibility in ABAP Cloud, side-by-side extensibility on BTP).
BTP's four pillars: application development and automation, integration, data and analytics, AI.
Required Practical Implementation:
Build a table mapping Odoo concepts to SAP concepts: apps to modules, models to tables or CDS entities, XML views to Fiori or UI5 views, server actions to event handlers or BAPIs. Mark any row you are unsure of.
Draw Procure-to-Pay and Order-to-Cash as flow diagrams, labelling the document created and the data changed at each step.
Open SAP Business Accelerator Hub, find a Business Partner or Purchase Order API, and record its base URL pattern, entity sets, and one sample payload.
Write a one-page 'BTP versus S/4HANA' explanation in your own words.
Verification / Mastery Check:
Give a 2-minute spoken explanation of how BTP relates to S/4HANA to someone with no SAP background.
Define 10 glossary terms from memory.
Classify 8 given scenarios correctly as in-app extension, side-by-side extension, or a core modification to avoid.
Module 0.2: API Basics
Granular Sub-topics & Mechanics:
HTTP anatomy: method, URL, headers, body, status line.
Methods: GET, POST, PUT, PATCH, DELETE, with safe versus idempotent behaviour.
Status codes: 200, 201, 204, 301, 302, 304, 400, 401, 403, 404, 405, 409, 415, 422, 429, 500, 502, 503, 504.
Headers: Content-Type, Accept, Authorization, Cache-Control, ETag, If-Match, Location, CORS headers.
Transport and state: statelessness, HTTPS and TLS at concept level, cookies versus tokens.
REST design: resources, URIs, representations, pagination, filtering, versioning.
JSON and YAML: JSON types, nesting and syntax rules; YAML mappings, sequences, indentation, multi-line strings, comments. Both appear later in mta.yaml and manifest.yml.
OData v4 structure: service root, $metadata, EntityType, EntitySet, key, NavigationProperty.
OData v4 query options: $select, $filter, $orderby, $top, $skip, $count, $expand, $search.
$filter syntax: the operators eq, ne, gt, ge, lt, le, and, or, not, and the functions contains, startswith, endswith.
OData operations: create, update and delete via POST, PATCH and DELETE; actions versus functions; $batch.
OData V2 versus V4: V2 is still common in S/4HANA APIs and UI5 models. Compare $inlinecount and $count, and the d.results JSON wrapper.
Tools: Postman (collections, environments, variables, test scripts) and curl.
Required Practical Implementation:
Use the public TripPin OData sample service to read $metadata and list its entity sets and keys.
Write 10 queries against it, covering select, filter, orderby, top, skip, count and expand.
Build a Postman collection with a baseUrl environment variable and 5 requests, each with a test script asserting the status code and the JSON shape.
Write one JSON document and its YAML equivalent. Introduce 3 deliberate syntax errors in each and read the parser messages.
Verification / Mastery Check:
From a $metadata document, hand-write 5 correct URLs for 5 stated requirements.
Classify 12 status-code scenarios correctly.
Explain why PUT is idempotent and POST is not.
Convert a nested JSON file to YAML and back with zero errors.
Module 0.3: JavaScript and Node.js
Granular Sub-topics & Mechanics:
Variables and types: var, let, const, hoisting, temporal dead zone; string, number, boolean, null, undefined, symbol, bigint; == versus ===; truthy and falsy values.
Functions: declarations, expressions, arrow functions, closures, default, rest and spread parameters, this binding.
Syntax features: destructuring, template literals.
Arrays and objects: map, filter, reduce, find, some, every, forEach, sort; Object.keys, Object.values, Object.entries; JSON.parse and JSON.stringify.
Modules: CommonJS (require, module.exports) versus ES modules (import, export).
Event loop: call stack, task queue, microtask queue.
Promises: pending, fulfilled, rejected; then, catch, finally; Promise.all, Promise.allSettled, Promise.race.
Async code: async and await, try/catch, Error objects, custom error classes.
Node.js runtime: process, process.env, fs/promises, path, the http module, global fetch.
npm: package.json, dependencies versus devDependencies, scripts, package-lock.json, semver ranges, npx, node_modules.
Express: routing, middleware order, request and response objects, error-handling middleware. CAP's Node runtime is built on Express.

Module 0.6: Auth Concepts
Granular Sub-topics & Mechanics:
Core ideas: authentication versus authorization, sessions versus tokens, password hashing at concept level, Basic authentication (Base64 is encoding, not encryption), API keys versus tokens.
OAuth 2.0 roles: resource owner, client, authorization server, resource server.
Grant types: authorization code with PKCE, client credentials, refresh token. The password and implicit grants are deprecated; know why.
OAuth 2.0 mechanics: scopes, access token versus refresh token, authorization endpoint versus token endpoint.
OpenID Connect: the ID token and how it differs from the access token.
JWT structure: header, payload, signature, base64url encoding; claims iss, sub, aud, exp, iat, nbf, scope.
JWT signing and validation: HS256 versus RS256, JWKS, and the validation steps (signature, issuer, audience, expiry).
SSO and access models: SSO via SAML 2.0 and OIDC at awareness level, RBAC versus ABAC, least privilege, and CORS and CSRF at awareness level.
Required Practical Implementation:
Draw sequence diagrams for authorization code with PKCE and for client credentials.
Decode a sample JWT locally with Node (Buffer.from(part, 'base64url')). Do not paste real tokens into online tools.
Generate an RSA key pair with openssl.
Write Express middleware using jsonwebtoken that rejects expired tokens, wrong audience and bad signatures.
Verification / Mastery Check:
Given 3 tokens, correctly identify which is valid, which is expired, and which has the wrong audience, by reasoning and by code.
Pick the right grant type for 6 scenarios.

Phase 3: CAP Development (the heart)
Core Objective: Model a domain in CDS, expose it as OData services, implement validation and business logic in Node.js handlers, persist data in SQLite for development and SAP HANA Cloud for the cloud, and test it automatically.
Estimated Time: about 40 hours over 3-4 weeks.
Module 3.1: CAP Fundamentals
Granular Sub-topics & Mechanics:
CAP idea: domain-driven model, services as the API layer, framework generating OData, persistence and runtime behaviour from the model.
File and namespace basics: namespace, using ... from, one concept per file, db/schema.cds versus srv/*.cds.
Types and elements: built-in types (String, Integer, Decimal, Boolean, Date, Time, DateTime, Timestamp, UUID, LargeString), custom type definitions, enums, key, not null, default.
Reuse: the cuid and managed aspects and Countries, Currencies, Languages from @sap/cds/common; your own aspect definitions; extend and annotate.
Associations: Association to, Association to many, managed associations and their generated foreign keys, Composition of many and Composition of one for parent-child lifecycles, and the difference between association and composition.
Special elements: localized elements and generated _texts entities, virtual elements, calculated elements, and @cds.persistence.skip.
Services: service definitions, exposing entities with as projection on, @readonly, @insertonly, @odata.draft.enabled, and redirected to for composition targets.
Projections and views: as select from, { * }, excluding, renamed elements, path expressions, where, group by, join basics.
Annotations basics: @title, @mandatory, @assert.range, @assert.format, @assert.target.
Required Practical Implementation:
Model a 5-entity domain of your choice (for example Suppliers, Products, Orders, OrderItems, Forecasts) with at least one managed association, one composition, one enum and cuid plus managed.
Expose it through two services: an admin service with full access and a read-only catalog service using projections.
Add a view that aggregates data, such as order totals per supplier.
Run cds compile to SQL and to EDMX for each service and read the output.
Verification / Mastery Check:
Predict from your CDS file the foreign key column names, the tables generated and the entity sets exposed, then confirm with cds compile.
Explain composition versus association with one deletion example.
Module 3.2: Service Implementation
Granular Sub-topics & Mechanics:
Handler registration: a .js or .ts file with the same name as the .cds service, or @impl, and cds.service.impl.
Request phases: srv.before, srv.on, srv.after, and the order handlers run in.
Events: CREATE, READ, UPDATE, DELETE, bound and unbound actions and functions, custom events.
Request object: req.data, req.query, req.params, req.target, req.user, req.locale, req.event.
Feedback: req.error, req.reject, req.info, req.warn, req.notify, HTTP status mapping, and returning structured error messages.
Querying: CQL builders SELECT.from, SELECT.one.from, INSERT.into, UPDATE.entity, DELETE.from, .where, .columns, .orderBy, .limit.
Service calls: cds.connect.to, srv.run, srv.send, srv.emit.
Validation layers: declarative @assert.*, @mandatory, @readonly, versus custom validation in before handlers.
Automatic values: @cds.on.insert, @cds.on.update, and managed fields.
Draft awareness: @odata.draft.enabled, draft lifecycle (NEW, EDIT, SAVE, CANCEL), and why validation runs on SAVE.
Testing: @cap-js/cds-test or cds.test, with Jest, and calling the running service in tests.
Required Practical Implementation:
Implement a bound action on Orders (for example submit) that changes a status and rejects invalid transitions with a 409.
Add a before handler that validates stock and quantity and returns multiple errors in one response.
Add an unbound function returning aggregated data computed with CQL.
Add an after READ handler that adds a computed field to results.
Write at least 10 Jest tests covering success, validation failure and not-found cases.
Verification / Mastery Check:
Show a request that triggers each of 400, 404 and 409 from your service, with the response body, and explain which layer produced each.
All tests pass with npm test.
Module 3.3: Data and Persistence
Granular Sub-topics & Mechanics:
Development database: SQLite in-memory with cds watch, persistent file with cds deploy --to sqlite:db.sqlite, and the @cap-js/sqlite package.
Test data: CSV files in db/data/ named <namespace>-<Entity>.csv, header rows, delimiter rules, and composition and association foreign key columns.
Database configuration: cds.requires.db and profiles such as [development] and [production] in package.json or .cdsrc.json.
Schema deployment: how the model becomes tables and views, cds build, and cds deploy.
Migrations: adding a field versus renaming or removing one, @cds.persistence.journal and migration tables for HANA, and what HDI can evolve automatically.
Transactions: one transaction per request, cds.tx, cds.context, commit and rollback, and what happens when a handler throws.
Concurrency: @odata.etag for optimistic concurrency with If-Match.
Performance basics: $select pushdown, indexes with @cds.persistence hints at awareness level, and avoiding N+1 queries in handlers.
Required Practical Implementation:
Create CSV test data for every entity of your domain and load it on cds watch.
Deploy to a persistent SQLite file, then add a column to an entity and redeploy.
Write a handler that updates two entities in one request and make the second update fail on purpose to prove the first rolls back.

Clean core: keeping custom code off the standard system, using released APIs and extension points only, and the A to D clean core levels. Verify the current definitions in SAP's clean core documentation.
Integration contracts: released APIs in SAP Business Accelerator Hub, business events (SAP Event Mesh and its successor offerings at awareness level), and webhooks.
Upgrade-safe design: never read standard tables directly, version your own APIs, decouple through events, replicate the minimum data, and add contract tests for the APIs you consume.
SAP system connectivity: destinations, Cloud Connector for on-premise systems, communication arrangements, scenarios and users in S/4HANA Cloud, OAuth2SAMLBearerAssertion and principal propagation, and generated OData clients with the SAP Cloud SDK.
Decision framework: choose in-app when it is a field or simple logic on a standard object, side-by-side when it needs its own data, UI, AI or life cycle, and avoid core modification.
Required Practical Implementation:
Take 3 requirements (for example an approval workflow, a custom report, and a forecast widget) and decide the extension style for each with a written justification. Your Odoo module experience gives you a useful comparison, so note what maps and what does not.
Draw the architecture of your forecast service as a side-by-side extension of S/4HANA, showing the released API it reads, the event it listens to, and the connectivity path.
Generate an OData client with the Cloud SDK from a Business Accelerator Hub API specification and call the sandbox.
Verification / Mastery Check:
Classify 10 given scenarios correctly.
Explain why your forecast service must not read S/4HANA tables directly, and what it uses instead.
